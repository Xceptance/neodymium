# [DEF-20261019-1529] Interactive Mode Step Confirmation Blocked After Before Block

- **Status:** `Resolved`
- **Opened:** 2026-10-19 13:05
- **Closed:** 2026-10-19 15:30
- **Component:** `neodymium-core`
- **Scope:** `Framework`
- **Symptom:** In interactive mode with a playbook containing lifecycle blocks (`before`, `steps`, `after`), transitioning from the `before` block to the first core step disabled the `Run` button (`btnRun.disabled = true`), preventing confirmation/execution of the active step. Furthermore, the "Step Details" panel displayed step #1 from the `before` block rather than the currently active core step, and step numbering badges displayed repeating/colliding indices (`#1`, `#1`, `#3`, `#4`, `#5`, `#1`).
- **Root Cause:** In `InteractiveStateBuilder.java`, steps across `before`, `steps`, and `after` blocks were each serialized using a local loop index `i = 0 .. size - 1`, setting `obj.addProperty("index", stepIndex + 1)`. Consequently, the step `index` restarted at `1` for each section, producing colliding indices across blocks. In `interactive_console.js`, `checkActionApprovals()` retrieved `data-step-idx` from the active card and looked up the step via `allSteps.find(st => st.index === idx)`. For core step 1 (`index: 1`), `find` matched `before[0]` (`index: 1`), which had status `"passed"`. Because `checkActionApprovals` detected that the matched step was `"passed"`, it unconditionally disabled `btnRun`. Similarly, `updateBigScreenDetails` and step selection resolved the first step in `before` instead of the active core step, and badge calculation `allStepIndices.indexOf(step.index) + 1` produced colliding `#1` badges.
- **Detection Gap ("What did we miss?"):** Prior lifecycle tests in `PlaybookLifecycleExecutionTest` verified that `blocks.before`, `blocks.steps`, and `blocks.after` contained the expected instructions and counts, but did not assert global uniqueness or continuous sequential ordering of `index` across blocks or test step lookup when transitioning from a completed `before` block to an active core step.
- **Resolution:** 
  1. Updated `InteractiveStateBuilder.java` to track a continuous `globalIndex` across `before`, `steps`, and `after` blocks, serializing `index` as `globalIndex + 1` (1..N globally unique), while preserving `blockIndex` (0-based relative index) and `block` (`"before"`, `"steps"`, `"after"`).
  2. Updated `serializeStep` to detect the active step using `ExecutionContext.KEY_CURRENT_PLAYBOOK_STEP` and match report entries and LLM calls by either `stepIndex` or `globalIndex`.
  3. Corrected `anyStepFailed` in `InteractiveStateBuilder.java` to only override state status when the report status is `"FAILED"`/`"ERROR"` or when the execution has completed, preventing spurious `"failed"` status overrides while the test runner is actively `"running"` or `"paused"`.
  4. Updated `interactive_console.js` `checkActionApprovals()` to look up the step within `currentState.blocks[blockName]` before falling back to `allSteps`.
  5. Added `testInteractiveStateBuilderGlobalContinuousStepIndexingAcrossBlocks` to `PlaybookLifecycleExecutionTest.java` verifying continuous global step indexing (1..N) and active status when transitioning from completed `before` steps to active core steps.
- **Safety Net Added:** Added `@Test` `PlaybookLifecycleExecutionTest.testInteractiveStateBuilderGlobalContinuousStepIndexingAcrossBlocks` explicitly verifying sequential global step indices across `before`, `steps`, and `after` blocks without index collisions, with correct block identifiers and relative block indices.
