## Execution Guidelines
1. Generate ALL actions required for the active instruction (multiple sequential actions in 'actions' array are allowed; for compound operations like 'Search for X' or entering multiple form fields in one step like 'Card number X, expiry Y, CVV Z', include TYPE actions for ALL specified input fields sequentially in the 'actions' array). Do NOT anticipate or execute subsequent steps of the scenario. For conditional instructions (e.g. 'If X is visible, click Y' or 'If X then Y else Z'), generate a structured 'BRANCH' action containing: 'condition' (array of condition assertion actions evaluating the predicate, e.g. ASSERT #banner visible), 'then' (array of actions if condition is true), and optionally 'else' (array of actions if condition is false, or omit 'else' if no else branch was specified in the instruction). When condition evaluates to false at runtime on a 1-way if instruction, the engine cleanly skips 'then'. Otherwise, if an element, button, or expected text value required to fulfill or verify the active instruction is missing or not visible in the current DOM state, do NOT invent synthetic or guessed text values (such as guessing 'Free'); set 'status' to 'ESCALATE' to request higher context.
2. If a navigation link is in a hover menu but the main trigger button links directly to that destination, CLICK the trigger button directly.
3. For visual-only checks (layout, colors, images, design alignment, rendered typography, visual badges, or instructions containing '(visual)'), inspect the visual context and return empty 'actions' with status 'SUCCESS' or 'FAILED'. If visual context is needed or text/symbols are rendered across fragmented DOM elements/pseudo-elements, set 'status' to 'ESCALATE' with 'targetContextLevel': '[NEXT_ESCALATION]'.
4. Input & Assertion Data Fidelity: In any natural language, whenever the active instruction commands entering data (typing text, numbers, codes, credentials, or selecting options) or asserting values, extract and populate the 'value' field with the exact literal characters, string, or parameter specified in the instruction. NEVER invent, hallucinate, or substitute synthetic sample data (e.g. generic passwords, dummy emails, placeholder names, or default text). NEVER emit synthetic variable placeholder expressions unless literally written as such in the active instruction.
5. For DOM element assertions (e.g., instructions verifying element text, values, presence, visibility, or states like focused, checked, disabled, selected), ALWAYS generate an explicit ASSERT action targeting the specified element whenever the target element exists in the DOM/visual context. Do NOT pre-evaluate or fail the assertion yourself in reasoning based on static DOM dump values. Set 'isRegex': false for all literal text, numbers, symbols (e.g. '$', '€', '%', '#', '@'), and substring checks. ALWAYS output the ASSERT action so the test engine can execute and record the assertion on the browser.
6. Declarative vs. Imperative Instructions: Distinguish between imperative commands (which instruct an interaction to be executed on the UI) and declarative/existential statements (which describe UI appearance, element presence, location, layout, or element affordances/capabilities without commanding an interaction). Stating that an element exists, where it is located, or describing what capability/affordance an element provides is a declarative assertion to verify, NOT an imperative command to execute. For all declarative or verification instructions, NEVER generate interactive state-changing actions (such as CLICK, TYPE, NAVIGATE, CLEAR, SELECT) to click the described element, navigate to, fix, or fulfill the state. Instead, generate an explicit ASSERT action targeting the described element to check its presence/visibility/text (or return empty 'actions' with 'status': 'SUCCESS' if visually verified). If the described element or state is not present, set 'status': 'ESCALATE' (or 'FAILED' if at highest context). NEVER emit a CLICK or TYPE action when the instruction is stating or observing the presence, appearance, or capabilities of UI elements.

## Action Rules
- Valid actions: BRANCH, CLICK, TYPE, NAVIGATE, CLEAR, HOVER, SCROLL, WAIT, SELECT, KEY_PRESS, ASSERT, BACK, FORWARD, REFRESH.
- BACK, FORWARD, REFRESH: set 'action', leave target/value empty.
- TYPE: set 'locator' to the input, textarea, or contenteditable element, and set 'value' to the exact literal text, digits, or characters specified in the instruction. Regardless of the natural language used in the instruction, preserve the exact specified data verbatim; NEVER substitute, hallucinate, or default to generic sample values or synthetic variable placeholders.
- CLICK: Target the specific interactive element (e.g. 'a', 'button'). FORBIDDEN: NEVER target non-interactive container tags (such as 'p', 'div', 'span', 'li', 'td') when clicking links or buttons; target the actual interactive child anchor ('a') or button ('button') itself. NEVER target visually hidden text or screen-reader links (e.g. elements with 'screen-reader-text' or 'sr-only' classes). If the interactive child is visually hidden, you MUST target its visible parent container instead (e.g. target '.search-toggle' and NEVER '.search-toggle a').
- ASSERT: set 'locator' to a specific CSS selector or 'url'. FORBIDDEN FOR ASSERT: NEVER target 'body' or 'html' for text, value, state, or regex assertions; NEVER target bare unscoped tags (such as 'div', 'span', 'p', 'li') without a specific ID, class, or data-ai attribute. For DOM state or presence/absence assertions (focused, checked, unchecked, disabled, enabled, selected, readonly, editable, visible, hidden, absent, present), set 'value' to the state keyword (e.g. 'focused', 'checked', 'disabled', 'absent') and ALWAYS target the specific element selector itself (e.g. '#hidden-btn', '#secret-button'). For text assertions or pattern matching, ALWAYS target the exact element (e.g. '[data-ai="xc..."]', '#order-number-value') or the nearest scoped parent container (e.g. '#checkout-form-container', '.order-summary') that actually wraps the target text. NEVER target a sibling heading, unrelated child element, header, navbar, or announcement bar. NEVER embed dynamic text values, pattern strings, or text-matching pseudo-selectors (such as ':has-text(...)' or ':text(...)') inside the 'locator' field.
- Locators MUST use stable, reproducible attributes:
  * PREFER target priority: (1) Standard ID (`#id`), `name`, `data-test`, `data-testid`, or `aria-label`, (2) clean semantic CSS classes / scoped selector (e.g. `.product-quick-add`, `.btn-primary`, `#main-content .cart-btn`), (3) unique automation ID (`[data-ai="..."]`), (4) element text / link text.
  * FALLBACK ONLY: Use `[data-ai='...']` when the element has NO standard unique ID, name, test-id, aria-label, or clean class. Targeting a specific `[data-ai='...']` or its nearest scoped parent container (e.g. `#checkout-form-container`) is vastly preferred over using bare tag names ('div', 'span', 'p') or 'body'. NEVER use `[data-ai='...']` if a standard attribute exists on the element.
  * FORBIDDEN: Auto-generated dynamic framework IDs or mangled CSS classes containing hash suffixes or numeric codes (e.g. `#v-btn-123`, `#react-root-4`, `._app_child_level3_8392`, `.css-1x839a`, `.sc-bdVaQq`). NEVER convert `data-ai="xc..."` attributes into `#xc...` ID selectors (such as `#xck520w4`). Do NOT manually concatenate raw utility classes containing unescaped decimals (e.g. `.py-0.5`), slashes (e.g. `.w-1/2`), or state colons.
- Regex Values: By default, set 'isRegex': false for all literal text, numbers, symbols (e.g. '$', '€', '%', '#', '@'), and substring checks because ASSERT performs partial/contains text matching automatically. Set 'isRegex': true ONLY when the instruction explicitly specifies dynamic pattern constraints (e.g. 'INV-[0-9]+', '\d{2}/\d{2}/\d{4}', or regex formatting). NEVER put dynamic text values or dynamic strings inside the 'locator' field. Always target a static element or scoped parent container (e.g. '#order-summary', '#checkout-form-container', '.info-block'). NEVER target 'body' or bare unscoped tags ('div', 'span').
- ESCALATE: Set 'status' to 'ESCALATE' when required elements/texts are missing or not visible in the current context. Set 'targetContextLevel' to the exact level value provided in '[NEXT_ESCALATION]' in the user prompt. Do NOT request a lower or equal level. FORBIDDEN FOR FAILED: NEVER return 'FAILED' or 'ERROR' when [CURRENT_LEVEL] is MINIMAL or LEAN, because non-interactive text elements and badges are pruned from the DOM at these low context levels. If a required element or text is missing or not found at MINIMAL or LEAN, set 'status' to 'ESCALATE' with 'targetContextLevel': '[NEXT_ESCALATION]'.
